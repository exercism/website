Internationalization Audit

The state of i18n across the Exercism website

A full-surface audit of translation extraction — Rails views, server-side copy, the React frontend, and multi-locale readiness. Where the site is internationalized, where it isn't, and what it would take to finish. v2 narrows the numbers to the translate-in-scope surface and re-checks whether the "missing keys" actually break in prod.

Bottom line

Once out-of-scope areas are excluded, this is a solidly-in-progress migration — not the "barely majority" the raw numbers suggested. In-scope Rails view coverage is 79% and the React frontend is 62% adopted (and effectively higher — most non-adopters are copy-free logic files). The real remaining work is concentrated, not diffuse: (1) server-side copy — mailer subjects, flash messages, and above all the Ruby view-component/presenter layer (~155 strings of nav/headers/tab-labels) — stays almost entirely hardcoded and is the single highest-leverage gap; (2) a handful of genuinely in-scope zero-i18n view areas remain (challenges, layouts, courses mailers); and (3) non-English content effectively doesn't exist — 1 of 126 locale files carries hu/nl, with no user-facing way to switch locale.

Net: the plumbing is being laid well on the two "view" layers. What's left is the presenter boundary, a few in-scope sections, and the fact that there's no populated second language or route to reach one yet.

01

Rails view templates

The most mature layer. Views use Rails' lazy-lookup convention (t('.key')) with locale YAMLs that mirror the view tree. Coverage is measured by key resolution, not file-mirroring — this repo consolidates many views into shared/renamed YAMLs, so a missing companion file ≠ a gap. Figures below are in-scope (admin/maintaining/bootcamp/test excluded).

In-scope template coverage — 365 templates (101 out-of-scope removed)289 full · 76 zero-i18n · 79.2%
Fully keyed (289) No i18n at all (76) v1 app-wide: 62.7% (292/466)
Load mechanism — verified, no loading bug. The initializer explicitly loads only 7 category dirs, but config/locales/views/** loads anyway via Rails' default config/locales/**/*.yml glob (all 115 view YAMLs confirmed present in I18n.load_path). The explicit loop harmlessly double-loads those 7 categories. Production sets config.i18n.fallbacks = true, so hu/nl requests silently fall back to English rather than erroring — which is exactly why the total non-coverage below is invisible in practice.

02

Key integrity

Of the keyed views, are the keys actually sound? Two failure modes: missing keys (referenced but absent → render translation missing) and orphan keys (defined but never referenced → dead weight). ~55 missing keys were found (the naive filename-mirror approach gives 1259 false positives; the real number needs merged-tree resolution). v2 re-triages each for prod reachability — because a referenced-but-absent key only breaks if the code path actually renders.

Reachability ≠ traffic — read this before acting. The triage is static: it proves these keys sit on routed, ungated code paths, not that real users hit them. The three carrier pages are low-traffic — a paid-course purchase-confirmation screen and two About pages — which plausibly explains the absence of bug reports better than "dead code" does. Whether they're live experiences (vs. merely live routes) depends on data static analysis can't see: are these courses still being sold? See the prod-check list at the end of this section.

Missing-key incidents by reachability verdict

  • reachable · low-traffic
    courses/enrolled — wrapper + 3 partials, ~37 keys

    GET /courses/enrolled is routed with no gating; it renders courses/enrolled/#{template_slug}. coding_fundamentals & front_end_fundamentals (16 keys each) have no matching YAML namespace at all; the wrapper is missing 4; the bundle partial misses 1 (create_one_here, guest-checkout branch). Renders on every course purchase confirmation — but only if these courses are still sold.

  • reachable · low-traffic
    about/testimonials.html.haml — 3 keys

    Routed at /about/testimonials, no testimonials.yml exists at all. .meta_title/.meta_description/.heading render unconditionally at the top of the template.

  • reachable · low-traffic
    about/team.html.haml — kaido_link_text ×2

    Link text inside a bio_html interpolation for two people; the key was never added alongside their other bio keys. Renders on every /about/team view.

  • dead — unrouted
    layouts/nav/front_end_fundamentals.html.haml — 11 keys

    Orphaned template. nav_submenus.rb wires no :front_end_fundamentals view value (grep-confirmed zero refs) — superseded by a nav redesign. Never rendered.

  • dead — prod-disabled
    temp/modals/donation_confirmation — thank_you_title

    Genuine key mismatch (YAML has thank_you_title_html), but moot: the whole temp/modals route is wrapped in unless Rails.env.production? ("TODO: Remove before launching"). Dev/staging-only preview scaffolding — cannot fire in prod.

Prod checks to close the reachability→traffic gap — three quick queries only the running app can answer:
  • Grep production logs for I18n::MissingTranslation / translation missing over the last 30–90 days — if the courses/about keys aren't there, they're effectively never rendered.
  • Check whether Coding Fundamentals / Front-End Fundamentals are still purchasable (live course records + recent enrollments) — if sales have stopped, the 37 courses/enrolled keys are dead in practice despite being live in code.
  • Confirm /about/testimonials and /about/team pageview volume — these are the only genuinely always-on carriers; if traffic is negligible, downgrade from "bug" to "cleanup."
Orphan keys — uneven by file age. Small, tightly-scoped YAMLs (settings/show, courses/pay) are essentially orphan-free. Large files that accreted content across refactors/campaigns carry real dead weight: tracks/build.yml (~8–10% — legacy nested tooltip feedback: blocks + a dead shared.* namespace), about/organisation_supporters_partners.yml (~35% — route is commented out, whole subtree unreachable), and cohorts/show.yml (stale "Aug '22" campaign partials). Interpolation-mismatch checking was inconclusive — the regex tool's false-positive rate was too high to trust; a proper AST pass would be needed.
03

Server-side copy — the biggest blind spot

Everything outside templates: controllers (flash/error messages), mailers (subjects & bodies), and — most consequentially — the Ruby view-component / presenter / react-component-helper layer that generates nav menus, headers, tab labels and status tags. This is where "fully migrated" pages still leak hardcoded English, because the template delegates its copy to a Ruby object that hardcodes it.

Evergreen mailer subjects and flash messages are ~0% internationalized. Zero I18n.t usage across the mailers — every subject is a hardcoded literal (e.g. "[Exercism] Reset password request", "Welcome to Exercism Insiders"). In-scope controller flashes (GitHub-syncer errors, moderation, unsubscribe) are the same. Emails and system notices cannot be localized without a structural pass here.

React frontend

There are two independent i18next systems: an interpreter-local one (Jiki runtime error messages) and a broad app-wide one at app/javascript/i18n/ feeding useAppTranslation. The app-wide system is a genuine, tooling-assisted migration in flight (LLM-assisted extract-jsx-copy / extract-haml-copy tooling present) — but only an en resource is registered, so it's English-only in practice.

05

Multi-locale readiness

Configuration says three locales; reality says one. This is the gap between "i18n-ready" and "actually multilingual."

  • 1 / 126
    Almost no non-English content exists

    Exactly one locale file — config/locales/pages/track.yml — carries hu and nl roots (and it's fully at parity, 34/34 keys). Every other file across views, mailers, devise, API and preferences is English-only. hu/nl are unpopulated everywhere else.

  • no UI path
    Locale switching is wired but unreachable

    ApplicationController runs around_action :switch_locale!, honoring params[:locale]. But nothing sets it: no scope "/:locale" in routes, no Accept-Language negotiation, no switcher UI, no user language preference driving I18n.locale. The only way to see hu/nl today is manually appending ?locale=hu — and even then only the one track.yml fragment renders translated.

  • context
    The translation program is still recruiting

    A "Become a translator" page gathers volunteers (its own copy says translation is targeted "near the start of September"). translator_locales is a volunteer-signup preference, not a consumption setting. The multi-locale config is best read as early scaffolding ahead of a localization drive, not a shipped feature.

06

Prioritized remediation

Ranked by impact-per-effort, assuming the goal is to make the site genuinely translatable end-to-end. Fix correctness first, then close the structural blind spots, then populate a language.

  1. Triage then fix the missing keys correctness

    Run the three prod checks in §02 first. ~44 keys sit on live routes but all on low-traffic pages (courses/enrolled/*, about/testimonials, about/team) — likely why no bug reports exist. If logs/sales confirm they render, fix them (small, bounded). If the courses are retired, delete the dead partials instead. The 12 confirmed-dead keys (orphan nav partial + prod-disabled modal) are pure cleanup.

  2. Internationalize the Ruby presenter layer structural

    ~155 strings across app/helpers/view_components & react_components. This is the highest-leverage gap: nav, headers and tab labels leak hardcoded English into pages that are otherwise "done." Until this is keyed, no page is fully translatable.

  3. Extract mailer subjects & flash messages structural

    All 33 subjects + controller flashes. Emails and system notices are currently un-localizable. Establish an I18n.t convention for mailers and a flash-key helper.

  4. Close the in-scope zero-i18n view areas coverage

    Now that out-of-scope areas are excluded, the real remaining view work is: challenges/ (~215 prose strings, the heavy one), the layouts/ mailer footer, and the evergreen courses_mailer templates. The tracks/ and journey/ tails are scattered, low-effort finishes. Consider codifying the scope exclusions (admin/maintaining/bootcamp/test) in the audit tooling so future coverage numbers report against the in-scope denominator by default.

  5. Sweep orphan keys & dead namespaces hygiene

    Prune the ~35% dead about/organisation_supporters subtree, legacy tracks/build tooltip blocks, and stale cohort partials. Low urgency, but shrinks the surface before a translatathon.

  6. Build a real locale path, then populate a language enablement

    Add routing/Accept-Language/switcher UI so switch_locale! is reachable, register a non-en resource for the React app-wide system, and only then run the translatathon. Populating hu/nl before the structural gaps above are closed would produce a half-translated experience.

Method & confidence. Findings come from eight parallel static analyses (v1: six sweeps; v2: a missing-key reachability triage + an in-scope coverage re-baseline). Techniques: view key-resolution against the merged I18n tree, missing/orphan-key resolution (mailer-path- and pluralization-aware), static route/branch reachability tracing, exhaustive per-file hardcoded-string extraction, and frontend adoption counts. String counts are catalogued exhaustively where marked "exhaustive" and are lower bounds elsewhere (regex sweeps favor precision, so they undercount multi-line and attribute strings). Interpolation-mismatch analysis was inconclusive and is not reported as a finding. No repository files were modified — this is read-only.

Key limitation — static, not runtime. Reachability is proven at the code level (routed? gated? dead branch?), not at the traffic level. The ~44 "reachable" missing keys sit on live routes but on low-traffic pages; whether real users render them depends on prod logs and course-sales data this audit cannot see. The three checks in §02 close that gap. Also unverified at runtime: whether stale cohort/campaign partials are reachable via live DB rows. These are decisions to confirm, not defects. Out-of-scope areas (admin, maintaining, bootcamp, test, campaign mailers) are excluded from all v2 headline figures per confirmed scope.
